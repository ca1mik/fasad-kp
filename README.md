# Автоматизированный аутрич для КП по фасадам

**Серверное рабочее место Fasad Flow:** запуск `start-product.cmd`, адрес `http://127.0.0.1:8770/work/`. Первый вход создаёт администратора. Клиенты, заявки, CAD, карты, склад и заказы полного интерфейса сохраняются в общей SQLite с проверкой версии. [Запуск, перенос данных, резервирование и текущие границы](PRODUCT_START.md).

Актуальное КП для просмотра от 15.10.2026: [готовый PDF](output/pdf/fasad-commercial-offer.pdf) · [редактируемая HTML-версия](sales/russia/fasad-offer.html). Три страницы: выгода для цеха, маршрут заказа, условия и приёмка пилота. Пересборка: `python scripts/build_premium_offer.py`. Действующее вложение автоматической рассылки не заменено.

CLI читает лиды из Google Sheets, готовит и отправляет письма через выбранного почтового провайдера, синхронизирует ответы и хранит локальное состояние в SQLite. Проект рассчитан на Python 3.12 и на один экземпляр развёртывания с одной общей базой состояния.

## Безопасный запуск

1. Установите Python 3.12.
2. Создайте и активируйте виртуальное окружение:

   ```powershell
   py -3.12 -m venv .venv
   .\.venv\Scripts\Activate.ps1
   python -m pip install --upgrade pip
   pip install -r requirements.txt
   ```

   В Linux/macOS активация выполняется командой `source .venv/bin/activate`.

3. Скопируйте `.env.example` в `.env` и заполните значения. Все секреты хранятся только в переменных окружения или в локальном `.env`; файл `.env` исключён из Git.
4. Дайте учётной записи Google доступ к таблице и настройте почту по разделам ниже.
5. Начните с проверок, которые ничего не отправляют:

   ```powershell
   python main.py healthcheck
   python main.py dry-run --sample
   python main.py state-report
   ```

Локальную веб-демонстрацию CRM можно открыть отдельной командой:

```powershell
python demo_server.py
```

## Настройка Google Sheets

Используется таблица с ID `1soUyxdgnlqU1hMRjtoHAeVii3qcPEMpsH6dXJeQbKqg`, лист `Лиды`. Доступ можно настроить одним из двух способов.

### Service Account

Создайте service account в Google Cloud, включите Google Sheets API, выпустите JSON-ключ и поместите весь JSON одной строкой в `GOOGLE_SERVICE_ACCOUNT_JSON`. Затем откройте таблицу в Google Sheets и предоставьте адресу `client_email` из JSON права редактора. Сам JSON-файл и его содержимое нельзя добавлять в репозиторий.

### OAuth пользователя

Создайте OAuth-клиент в Google Cloud, включите Google Sheets API и получите refresh token с доступом к таблицам. Заполните `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` и `GOOGLE_OAUTH_REFRESH_TOKEN`. Не заполняйте одновременно OAuth-переменные и `GOOGLE_SERVICE_ACCOUNT_JSON`, чтобы способ авторизации был однозначным.

Для Google OAuth можно локально запустить помощник (он откроет официальную страницу согласия Google):

```powershell
python auth_setup.py google-oauth --client-id "ВАШ_ID" --client-secret "ВАШ_SECRET" --purpose sheets
```

Команда выводит refresh token один раз. Сразу перенесите его в `.env` или secret store OpenClaw и очистите историю терминала, если она сохраняет вывод. Для service account доступна локальная проверка: `python auth_setup.py check-service-account "путь-к-json"`.

## Настройка почты

Выберите `MAIL_PROVIDER`: `gmail`, `outlook`, `yandex`, `mailru` или `smtp`. В `MAIL_ADDRESS` укажите полный адрес отправителя, а в `MAIL_DISPLAY_NAME` — отображаемое имя.

- `MAIL_AUTH_MODE=oauth`: заполните `OAUTH_CLIENT_ID`, `OAUTH_CLIENT_SECRET`, `OAUTH_REFRESH_TOKEN` и `OAUTH_TOKEN_URL`. Для Gmail токен должен иметь полный почтовый scope `https://mail.google.com/`, поскольку приложению нужны SMTP-отправка и IMAP-чтение ответов.
- `MAIL_AUTH_MODE=app_password`: заполните `MAIL_APP_PASSWORD`. Для Gmail, Yandex, Mail.ru и других провайдеров создайте отдельный пароль приложения в настройках аккаунта; обычный пароль учётной записи использовать не следует.
- Для `MAIL_PROVIDER=smtp` задайте `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY` (`starttls` или `ssl`), `IMAP_HOST`, `IMAP_PORT` и при необходимости `IMAP_FOLDER`. Для преднастроенных провайдеров эти поля можно оставить пустыми, если приложение предоставляет их стандартные значения.

Перед реальной отправкой выполните `healthcheck`. Проверяйте правила провайдера, согласие получателей и применимые требования к деловой рассылке.

Для Gmail OAuth помощник запускается с `--purpose mail`; вариант `--purpose both` запрашивает одновременно доступ к Sheets и Gmail. У Microsoft, Yandex и Mail.ru используйте OAuth/app-password процедуру самого провайдера и укажите выданный refresh token или пароль приложения в `.env`.

## Рабочий цикл

`healthcheck` проверяет конфигурацию, доступ к листу и обязательным колонкам, SMTP-авторизацию и чтение IMAP без отправки. `dry-run` читает реальные лиды и показывает итоговые письма, но не меняет таблицу. Опция `--sample` полностью локальна и нужна для проверки установки.

`send-new` при `DRY_RUN=true` завершается с защитной ошибкой. При `DRY_RUN=false` он выбирает только подтверждённые новые производства, применяет дневной лимит, резервирует каждое письмо в SQLite, отправляет его и лишь после подтверждения SMTP записывает статус, дату и Message-ID в таблицу.

`sync-replies` читает ответы по `In-Reply-To`/`References`. При `DRY_RUN=true` он только показывает план обновлений; при `false` записывает ответ и консервативно выбирает статус. Заинтересованные и неясные ответы остаются для ручной обработки. Автоматических ответов и follow-up писем в проекте нет; `ENABLE_FOLLOWUPS=false` зарезервирован для будущего расширения.

## Гарантия от повторной отправки

Перед SMTP-вызовом приложение атомарно резервирует письмо в локальной SQLite-базе. Это даёт семантику at-most-once в пределах одного развёртывания и одного файла `STATE_PATH`:

- письмо, уже успешно отправленное или зарезервированное, повторно не выбирается;
- если SMTP вернул неопределённый результат (например, соединение оборвалось после передачи письма), запись получает статус `uncertain` и блокируется до ручной проверки; автоматически повторять её нельзя, потому что письмо могло дойти;
- статус `commit_pending` означает, что SMTP уже подтвердил отправку, но фиксация результата в Google Sheets не завершилась. Следующий запуск восстанавливает такую запись и завершает фиксацию **без повторной отправки письма**;
- резервирование, оставшееся на границе сбоя, сохраняется в журнале и не превращается в автоматическую повторную попытку.

Никогда не удаляйте SQLite-файл, чтобы «сбросить» очередь: вместе с ним исчезнет защита от дублей. Сделайте резервную копию и разберите записи через `state-report`. Гарантия действует только при одном развёртывании с одним локальным файлом SQLite. Не запускайте копии проекта на нескольких машинах с отдельными базами; сетевой файловый ресурс для SQLite также не является заменой общей транзакционной БД. Планировщик должен ссылаться на тот же каталог проекта и тот же `STATE_PATH`.

## Планировщик OpenClaw

По актуальной документации OpenClaw расписание можно передать первым позиционным аргументом, `--command-argv` задаёт точный массив аргументов без shell-разбора, а `--command-cwd` фиксирует рабочий каталог. См. [справочник CLI OpenClaw Automations](https://docs.openclaw.ai/cli/cron) и [правила расписаний](https://docs.openclaw.ai/automation/cron-jobs/schedules).

Пример для Linux, где проект размещён в `/srv/kp-fasad`:

```bash
openclaw automations create "0 10 * * 1-5" \
  --name "fasad-send-new" \
  --command-argv '["/srv/kp-fasad/.venv/bin/python","main.py","--env-file",".env","send-new"]' \
  --command-cwd "/srv/kp-fasad" \
  --tz "Europe/Moscow" \
  --no-deliver

openclaw automations create "15 * * * *" \
  --name "fasad-sync-replies" \
  --command-argv '["/srv/kp-fasad/.venv/bin/python","main.py","--env-file",".env","sync-replies"]' \
  --command-cwd "/srv/kp-fasad" \
  --tz "Europe/Moscow" \
  --no-deliver
```

Эти команды **регистрируют** задачи только при ручном выполнении. Репозиторий сам ничего не регистрирует. Сначала выполните `openclaw automations --help`, проверьте путь и затем просмотрите созданные задания через `openclaw automations list`. Скрипты `scripts/show_scheduler_examples.sh` и `scripts/show_scheduler_examples.ps1` лишь печатают подходящие команды и не выполняют их.

## Обычный cron в Linux

Обёртка `scripts/run_outreach.sh` переходит в каталог проекта, выбирает `.venv/bin/python` и возвращает код завершения CLI. Пример строк для ручного добавления через `crontab -e`:

```bash
chmod +x scripts/run_outreach.sh scripts/show_scheduler_examples.sh
```

```cron
CRON_TZ=Europe/Moscow
0 10 * * 1-5 flock -n /tmp/fasad-outreach.lock /srv/kp-fasad/scripts/run_outreach.sh send-new >> /srv/kp-fasad/logs/scheduler.log 2>&1
15 * * * * flock -n /tmp/fasad-outreach.lock /srv/kp-fasad/scripts/run_outreach.sh sync-replies >> /srv/kp-fasad/logs/scheduler.log 2>&1
```

`flock` не допускает перекрытия локальных запусков. Он не координирует разные серверы, поэтому правило одного развёртывания всё равно обязательно. Создайте каталог `logs` заранее и убедитесь, что пользователь cron может читать `.env` и писать в `data` и `logs`.

## Планировщик заданий Windows

Обёртка `scripts\run_outreach.ps1` использует Python из `.venv` и возвращает его код завершения. Следующие примеры только показывают команды; запускать их нужно вручную из PowerShell с подходящими правами:

```powershell
$project = 'C:\apps\kp-fasad'
$runner = Join-Path $project 'scripts\run_outreach.ps1'

schtasks.exe /Create /TN 'Fasad Outreach - Send New' /SC WEEKLY /D MON,TUE,WED,THU,FRI /ST 10:00 /TR "powershell.exe -NoProfile -ExecutionPolicy Bypass -File `"$runner`" send-new" /F
```
